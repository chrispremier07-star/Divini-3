 I. DIRECTIVES DE FUSION ET D'EXÉCUTION — RÈGLES SUPÉRIEURES

 I.1 Mission de l'agent

Tu es simultanément :
- architecte logiciel senior ;
- ingénieur frontend ;
- ingénieur backend ;
- ingénieur base de données ;
- ingénieur sécurité ;
- ingénieur QA ;
- ingénieur DevOps ;
- spécialiste SaaS multi-tenant ;
- concepteur UX/UI ;
- intégrateur IA ;
- spécialiste des intégrations et plateformes externes.

Tu dois raisonner sur l'ensemble du système avant de modifier une partie. Tu dois comprendre les dépendances, préserver l'existant, construire progressivement, tester, corriger, vérifier et rendre compte.

 I.2 Vérité technique absolue

- Ne jamais transformer l'application en simple maquette.
- Ne jamais créer de bouton fictif.
- Ne jamais simuler une donnée, un statut, un paiement, une API ou une réussite comme si elle était réelle.
- Ne jamais déclarer une fonctionnalité terminée sans validation réelle.
- Ne jamais inventer une API, une règle externe, un quota, un tarif ou une capacité.
- Ne jamais coder en dur une règle externe susceptible d'évoluer lorsque sa configuration peut être centralisée.
- Ne jamais masquer une limitation technique.
- Ne jamais supprimer une fonctionnalité existante sans autorisation.
- Ne jamais casser une route, un composant, un service ou une intégration existante.
- Ne jamais laisser une action sensible dépendre uniquement du frontend.

 I.3 Préservation de l'existant

Avant toute modification :
1. analyser l'architecture ;
2. identifier les fichiers/composants/services existants ;
3. identifier les modèles et données ;
4. identifier la base et les migrations ;
5. identifier l'authentification ;
6. identifier RBAC et permissions ;
7. identifier logs/audit ;
8. identifier intégrations ;
9. identifier queues/workers ;
10. identifier facturation ;
11. identifier les composants réutilisables ;
12. identifier les conventions et dépendances.

Réutiliser ce qui est sain. Éviter toute duplication inutile. Ne pas réécrire ce qui fonctionne sans nécessité démontrée.

 I.4 Développement par lots

Chaque lot doit suivre obligatoirement :

ANALYSER → PLANIFIER → CONSTRUIRE → INTÉGRER → TESTER → CORRIGER → VALIDER → DOCUMENTER

Avant le codage d'un lot, fournir :
- architecture concernée ;
- fichiers créés ;
- fichiers modifiés ;
- migrations DB ;
- services ;
- routes API ;
- composants ;
- permissions ;
- tests ;
- dépendances ;
- risques ;
- stratégie de non-régression.

Après le lot :
- compiler/build ;
- exécuter les tests ;
- vérifier migrations ;
- vérifier API ;
- vérifier permissions ;
- vérifier persistance ;
- vérifier erreurs ;
- vérifier scénarios métier ;
- vérifier états vides/loading/offline ;
- vérifier responsive ;
- vérifier synchronisation ;
- vérifier logs/audit ;
- vérifier performances critiques ;
- vérifier non-régression.

Ne jamais passer au lot suivant si le lot courant n'est pas réellement fonctionnel.

 I.5 Frontend et backend en parallèle

L'interface ne doit jamais être repoussée à la fin. Construire frontend, backend, données et intégrations au fur et à mesure.

Tout élément visuel nouvellement implémenté doit être signalé pour vérification immédiate.

 I.6 Rapport obligatoire après chaque lot

Produire :
1. Implémenté ;
2. Visible maintenant ;
3. Backend uniquement ;
4. Tests effectués ;
5. Erreurs rencontrées et corrections ;
6. Régressions ;
7. Avancement global réel en %.

Ne jamais gonfler artificiellement l'avancement.

 CORPUS CANONIQUE PRINCIPAL — DIVINI EXO

 0. DIRECTIVE SUPRÊME

Tu es l'agent principal responsable de la conception, du développement, de l'intégration, de la sécurisation, du test, de la validation et de l'évolution de DIVINI EXO.

DIVINI EXO n'est PAS un prototype.

DIVINI EXO n'est PAS une simple maquette UI.

DIVINI EXO n'est PAS une démonstration simulée.

DIVINI EXO doit devenir une véritable plateforme SaaS ERP multi-tenant exploitable en production, conçue dès l'origine pour évoluer progressivement de :

100 → 1 000 → 10 000 → 100 000+ entreprises et utilisateurs, sans nécessiter une refonte fondamentale de l'architecture.

L'architecture doit également pouvoir supporter, lorsque l'infrastructure sera dimensionnée en conséquence, des volumes de données et d'utilisateurs extrêmement importants.

La priorité absolue est :

FIABILITÉ → SÉCURITÉ → INTÉGRITÉ DES DONNÉES → SCALABILITÉ → PERFORMANCE → EXTENSIBILITÉ → UX → ESTHÉTIQUE.

Ne jamais sacrifier la fiabilité métier au profit de la vitesse de développement ou de l'apparence visuelle.

Nom officiel :

DIVINI exo

> entreprise → parle → comprend → décide → agit.

Il ne doit pas simplement enregistrer ce que l'entreprise fait.

Il doit également :

- comprendre ;
- analyser ;
- surveiller ;
- anticiper ;
- recommander ;
- alerter ;
- automatiser ;
- assister ;
- sécuriser ;
- expliquer ;
- aider à décider.

La puissance fonctionnelle doit être cachée derrière une interface extrêmement simple.

Ne jamais transformer la richesse fonctionnelle en surcharge visuelle.

 6. ARCHITECTURE MULTI-TENANT

L'isolation multi-tenant est une exigence absolue.

Tenant A ne doit jamais pouvoir accéder aux données de Tenant B.

Cela doit être garanti :

- frontend ;
- backend ;
- API ;
- base de données ;
- stockage ;
- queues ;
- workers ;
- cache ;
- logs ;
- analytics ;
- webhooks ;
- IA ;
- exports ;
- imports ;
- fichiers ;
- intégrations externes.

Chaque donnée métier sensible doit être rattachée à son contexte organisationnel approprié.

Ne jamais se contenter d'une protection frontend.

Toute sécurité critique doit être vérifiée côté backend.

---

 7. ORGANISATION D'UN TENANT

Le tenant central peut créer plusieurs établissements / points de vente / agences.

Chaque établissement doit posséder ses propres :

- utilisateurs autorisés ;
- opérations ;
- caisse ;
- ventes ;
- mouvements ;
- statistiques ;
- stock selon configuration ;
- activités.

Mais les données doivent rester rattachées au tenant central.

Le tenant central doit pouvoir consulter des données consolidées.

Les utilisateurs d'un établissement ne doivent voir que les données autorisées.

---

 8. CRÉATION D'UN NOUVEL ÉTABLISSEMENT

Lorsqu'un tenant crée un nouvel établissement :

1. saisir les informations ;
2. calculer le supplément tarifaire ;
3. ajouter le supplément à l'abonnement ;
4. créer la demande ;
5. soumettre au créateur du SaaS ;
6. attendre validation ;
7. notifier le tenant central après validation ;
8. activer l'établissement ;
9. démarrer une période d'essai de 7 jours pour ce nouvel établissement lorsque les règles commerciales le prévoient.

La validation par le créateur du SaaS est obligatoire.

Après validation :

afficher une confirmation premium avec message de félicitation.

Une animation Lottie de confettis peut être utilisée à cet endroit uniquement.

Aucune animation décorative inutile ailleurs.

---

 9. ABONNEMENTS ET MONÉTISATION

Le SaaS possède :

 Module de base

Le module de base possède un prix défini par le créateur du SaaS.

 Modules complémentaires

Chaque module complémentaire possède son propre prix.

Le prix mensuel final du tenant doit être calculé dynamiquement :

Abonnement de base + somme des modules complémentaires + éventuels établissements supplémentaires + éventuels services facturables.

Les modules doivent être :

- activables ;
- désactivables ;
- commercialisables individuellement ;
- commercialisables en groupe ;
- associés à des plans ;
- configurables par le créateur du SaaS.

 12. RÉABONNEMENT

- conserver l'historique ;
- notifier le tenant.

Si un tenant renouvelle avant l'échéance, le calcul doit respecter la règle commerciale définie autour de la date d'abonnement initiale.

Ne jamais modifier silencieusement les dates historiques.

 18. COPILOT — CERVEAU DE L'ERP

COPILOT n'est pas un chatbot décoratif.

C'est un opérateur intelligent connecté aux données autorisées de l'ERP.

L'utilisateur peut demander :

> Pourquoi mon chiffre d'affaires baisse ?

L'IA doit pouvoir analyser :

- ventes ;
- clients ;
- produits ;
- marges ;
- stocks ;
- commerciaux ;
- périodes ;
- fournisseurs ;
- dépenses ;
- trésorerie.

Elle doit fournir :

1. constat ;
2. causes ;
3. données utilisées ;
4. recommandations ;
5. actions possibles.

Exemple :

CA -8,4 %.

Puis :

- 72 % de la baisse provient de 4 clients ;
- produit X représente 61 % de la baisse ;
- 3 clients importants n'ont pas commandé depuis 30 jours.

Puis :

Actions recommandées

- relancer ;
- analyser le produit ;
- analyser le prix ;
- examiner le stock.

Le bouton :

Exécuter les recommandations

doit déclencher un workflow sécurisé et contrôlé.

 20. AUTOPILOT — LIMITES ABSOLUES

L'IA ne doit jamais effectuer seule :

- transaction financière critique ;
- paiement ;
- transfert d'argent ;
- suppression massive irréversible ;
- modification comptable critique ;
- modification de permissions critiques.

Certaines actions automatisables sont autorisées, notamment :

- relances ;
- notifications ;
- génération de contenu ;
- préparation de commandes ;
- suggestions ;
- programmation de contenus ;
- réponses non sensibles.

Toujours appliquer :

Permission → règle → validation → action → audit.

 II. ENRICHISSEMENTS CANONIQUES ISSUS DE LA SECONDE SOURCE

Les règles suivantes complètent et précisent le corpus principal. Lorsqu'elles détaillent une règle déjà présente,
elles font foi dans leur formulation la plus opérationnelle.

 II.1 Produit et architecture

DIVINI EXO doit être :
- multi-tenant ;
- multi-boutiques / points de vente ;
- multi-agences ;
- multi-entrepôts ;
- multi-caisses ;
- API-first ;
- modulaire ;
- extensible ;
- responsive ;
- offline-first lorsque nécessaire ;
- compatible avec les connexions instables ;
- capable de synchronisation différée ;
- conçu pour plusieurs milliers puis potentiellement des millions d'utilisateurs selon le dimensionnement réel ;
- orienté automatisation et IA ;
- adapté au contexte ivoirien et africain.

 II.2 Expérience « zéro formation »

L'utilisateur doit pouvoir exprimer naturellement :
- « Je veux créer une facture. »
- « Je veux enregistrer une dépense. »
- « Je veux voir mes bénéfices du mois. »

Le système doit comprendre l'intention et guider vers le processus approprié sans transformer l'ERP en interface complexe.

 II.3 Proactivité quotidienne renforcée

Lors de la première connexion de la journée, l'IA peut proposer vocalement un point sur la veille, avec une décision explicite de l'utilisateur :
- OUI ;
- NON / PAS MAINTENANT.

Avec accord, elle peut dresser un bilan fidèle des transactions, relances, prospects, clients, publications programmées, échéances et événements pertinents, puis proposer les actions nécessaires.

 II.4 Pilote automatique renforcé

Le mode AUTOPILOT peut analyser situation actuelle, historiques, mouvements, habitudes et processus récurrents.
Il peut, dans son périmètre autorisé :
- envoyer des relances WhatsApp Business ;
- générer/programmer du contenu ;
- répondre à des messages clients ;
- effectuer certaines tâches non sensibles.

Il ne doit jamais prendre seul une décision financière critique, effectuer un paiement/transfert, modifier une permission critique ou exposer des informations sensibles.

Toute action doit respecter :
permission → règle → validation si requise → action → audit.

 II.5 Social Media enrichi

Le module Social Media doit être activable/désactivable comme les autres modules et intégrer au minimum Facebook, Instagram et TikTok.
Il doit gérer calendrier/grille, import image/vidéo, génération IA, contexte marque/audience/objectifs, prévisualisation, programmation, multi-réseaux, rappels, statistiques et suggestions IA.

Les dates/heures passées doivent être bloquées côté frontend ET backend.

 II.6 CRM, fidélité et catégories

Le CRM doit permettre segmentation extensible, historique, commandes, CA, panier moyen, LTV, tags, VIP, activité, sources, communication et consentements.

Exemple de règle VIP configurable :
10+ achats ET CA total >= 500 000 FCFA.

Pour les catégories produits, permettre à l'utilisateur autorisé de fournir quelques mots-clés et à l'IA de proposer une liste ; l'utilisateur peut supprimer, modifier, valider et persister les catégories retenues.

 II.7 Offline-first renforcé

Le fonctionnement hors connexion peut aller jusqu'à 7 jours selon la règle métier.
Chaque opération offline doit posséder :
- identifiant unique ;
- timestamp ;
- utilisateur ;
- établissement ;
- type ;
- statut de synchronisation ;
- version ;
- mécanisme anti-duplication.

La synchronisation doit être idempotente et ne jamais créer deux transactions à partir d'une répétition.

 II.8 API et plateforme

Prévoir OAuth 2.0, scopes, clés restreintes, rate limiting, révocation, audit, sandbox, webhooks, documentation et Developer Portal.
Préparer une future Marketplace soumise à validation, sécurité, permissions, isolation et conformité.

 II.9 Données personnelles et consentements

Le consentement doit être une donnée métier centrale, historisée, vérifiable et non modifiable silencieusement.
Prévoir une page de préférences client sécurisée par token aléatoire, long, non prédictible et révocable, sans accès aux données privées.

Le client doit pouvoir gérer :
- opt-out global ;
- opt-out par catégorie ;
- appels uniquement ;
- marketing uniquement ;
- relances uniquement.

 II.10 Règle de transparence WhatsApp

Toujours séparer :
CONSENTEMENT → ÉLIGIBILITÉ → POLITIQUES INTERNES → TEMPLATE → LIMITES/QUALITÉ → QUEUE → PLATFORM → WEBHOOK → STATUT FINAL.

Ne jamais promettre une gratuité sur la seule base d'une limite d'envoi.
Ne jamais confondre :
- limite ;
- gratuité ;
- coût estimé ;
- coût réel.

 II.11 Règle de vérité opérationnelle

Le résultat attendu est une application :
cohérente + persistante + réellement connectée + testée + sécurisée + exploitable + extensible.

Aucun faux bouton.
Aucune fausse donnée.
Aucun faux statut.
Aucune simulation cachée.
Aucun contournement de sécurité.
Aucun contournement de Meta.
Aucune régression volontaire.

 MODULE DE CONSENTEMENT WHATSAPP BUSINESS — SPÉCIFICATION TECHNIQUE ET FONCTIONNELLE

 OBJECTIF PRINCIPAL

Intégrer au module Client/CRM de l’ERP un système professionnel, sécurisé, traçable et auditable de gestion des consentements WhatsApp Business.

Le système doit permettre à l’entreprise de savoir précisément :

 quels types de communications un client accepte ;
 quels types de communications il refuse ;
 quand et comment chaque consentement a été obtenu ;
 par quel canal ;
 par quel utilisateur ou processus ;
 quelle preuve existe ;
 quand le consentement a été modifié ou révoqué ;
 pourquoi un client est actuellement éligible ou non à une communication WhatsApp.

IMPORTANT :

Ne jamais considérer une simple case cochée par un employé comme une preuve suffisante de consentement.

Le champ de permission affiché dans la fiche client doit être la représentation de données de consentement réellement enregistrées dans une structure dédiée et auditable.

Le système doit également distinguer le consentement interne enregistré dans l’ERP des mécanismes, contrôles, limites, templates, règles de qualité et politiques appliqués par WhatsApp Business Platform.

L’ERP ne doit jamais prétendre qu’un client est « certifié consentant par WhatsApp ».

Le système doit plutôt déterminer si l’entreprise possède une base de consentement suffisante et documentée pour contacter ce client, puis laisser l’envoi officiel WhatsApp Business Platform appliquer ses propres règles et contrôles.

API, intégrations externes et écosystème développeurs

Concevoir l’ERP dès maintenant comme une plateforme API-first ouverte, permettant à des applications, sites web, logiciels partenaires et services externes d’intégrer certains modules de l’ERP sans accès direct à la base de données.

Les principaux modules doivent être conçus pour pouvoir être exposés progressivement via API : clients, produits, stocks, ventes, commandes, factures, paiements, dépenses, fournisseurs, documents, comptabilité, utilisateurs, rapports, etc.

Mettre en place une architecture sécurisée basée sur OAuth 2.0, scopes/permissions granulaires, clés API restreintes, isolation multi-tenant, rate limiting, révocation des accès et journal d’audit. Une application externe ne doit accéder qu’aux données et actions explicitement autorisées.

Créer une section « Applications & intégrations » permettant à l’administrateur de consulter les applications connectées, les permissions accordées, leur activité, leur dernière utilisation et de révoquer immédiatement un accès.

Créer également un Developer Portal avec documentation API, endpoints, scopes, exemples de requêtes/réponses, clés de test, environnement Sandbox, webhooks et outils de test.

Implémenter des webhooks événementiels permettant aux applications autorisées de recevoir automatiquement les événements importants : création ou paiement d’une facture, nouvelle commande, stock faible, paiement reçu, nouveau client, dépense approuvée, etc.

Politique commerciale des API

Ne pas facturer les appels API au lancement. L’accès API doit être inclus dans les abonnements ERP selon le plan souscrit, afin de favoriser l’adoption et la création d’un véritable écosystème autour de la plateforme.

Prévoir néanmoins des quotas, limites de débit et règles d’utilisation raisonnables par plan, avec suivi de la consommation, alertes et protection contre les abus ou utilisations excessives.

Les utilisateurs doivent toujours pouvoir consulter leur quota, leur consommation et les limites applicables.

Ne pas créer de facturation à la requête par défaut. Si, à l’avenir, l’API devient une infrastructure utilisée massivement par des plateformes externes ou des entreprises qui ne sont pas clientes de l’ERP, prévoir la possibilité d’introduire séparément une offre API-as-a-Service / Enterprise avec tarification adaptée, sans nécessiter de refonte de l’architecture.

Écosystème et Marketplace

Prévoir une architecture permettant à terme de créer une Marketplace d’intégrations, avec applications officielles, partenaires et applications privées.

Toute application publiée devra être soumise à validation préalable et respecter les exigences de sécurité, permissions, isolation des données et conformité définies par la plateforme.

L’objectif est que chaque module puisse fonctionner à la fois comme fonctionnalité native de l’ERP et comme service intégrable par des plateformes externes, tout en conservant un contrôle total sur les accès, les données et la sécurité.

Construire cette architecture dès maintenant de manière extensible, sécurisée et rétrocompatible, afin de pouvoir faire évoluer ultérieurement les quotas, plans, permissions, fonctionnalités API et éventuelles offres commerciales sans casser les intégrations existantes.

  /* ---------- KPI count-up ---------- */
  function easeOutCubic(t){ return 1 - Math.pow(1 - t, 3); }

  function animateValue(el){
    var target = parseFloat(el.getAttribute('data-target'));
    var suffix = el.getAttribute('data-suffix') || '';
    var decimals = parseInt(el.getAttribute('data-decimals') || '0', 10);
    var duration = 1100;
    var start = null;

    function frame(ts){
      if (start === null) start = ts;
      var progress = Math.min((ts - start) / duration, 1);
      var eased = easeOutCubic(progress);
      var current = target * eased;
      var display = decimals > 0
        ? (current / Math.pow(10, decimals)).toFixed(decimals)
        : Math.round(current).toLocaleString('fr-FR');
      el.textContent = display + suffix;
      if (progress < 1) requestAnimationFrame(frame);
      else {
        var finalVal = decimals > 0 ? (target / Math.pow(10, decimals)).toFixed(decimals) : target.toLocaleString('fr-FR');
        el.textContent = finalVal + suffix;
      }
    }
    requestAnimationFrame(frame);
  }

  document.querySelectorAll('.kpi-value[data-target]').forEach(function(el){
    animateValue(el);

  function withFlip(mutate){
    var cards = kanbanBoard.querySelectorAll('.kanban-card');
    var firstRects = new Map();
    cards.forEach(function(c){ firstRects.set(c, c.getBoundingClientRect()); });
    mutate();
    cards.forEach(function(c){
      var first = firstRects.get(c);
      var last = c.getBoundingClientRect();
      var dx = first.left - last.left;
      var dy = first.top - last.top;
      if (dx || dy){

        c.style.transform = 'translate(' + dx + 'px,' + dy + 'px)';
        requestAnimationFrame(function(){
          c.style.transition = 'transform 300ms cubic-bezier(.2,.8,.2,1)';
          c.style.transform = '';
        });
      }
    });

  function getDragAfterElement(container, y){
    var cards = Array.prototype.slice.call(container.querySelectorAll('.kanban-card:not(.dragging)'));
    return cards.reduce(function(closest, child){
      var box = child.getBoundingClientRect();
      var offset = y - box.top - box.height / 2;
      if (offset < 0 && offset > closest.offset) return { offset: offset, element: child };
      return closest;
    }, { offset: Number.NEGATIVE_INFINITY, element: null }).element;

        else list.insertBefore(dragging, afterElement);
      });
    });

  var overlay = document.getElementById('commandOverlay');
  var input = document.getElementById('commandInput');
  var list = document.getElementById('commandList');
  var searchTrigger = document.getElementById('searchTrigger');
  var activeIndex = 0;
  var lastFocused = null;

  var commands = [
    { label: 'Aller à Aperçu', section: 'Navigation', run: function(){ switchTab('overview'); } },
    { label: 'Aller à Stock', section: 'Navigation', run: function(){ switchTab('inventory'); } },
    { label: 'Aller à Commandes fournisseurs', section: 'Navigation', run: function(){ switchTab('orders'); } },
    { label: 'Aller à Fournisseurs', section: 'Navigation', run: function(){ switchTab('suppliers'); } },
    { label: 'Créer une commande fournisseur', section: 'Actions', run: function(){ toast('Nouvelle commande créée', 'success'); } },
    { label: 'Synchroniser le stock', section: 'Actions', run: function(){ syncBtn.click(); } },
    { label: 'Exporter le rapport mensuel', section: 'Actions', run: function(){ toast('Export du rapport en cours…', 'info'); } },
    { label: 'Inviter un membre de l’équipe', section: 'Équipe', run: function(){ toast('Invitation envoyée', 'success'); } },
    { label: 'Marquer PO-4460 comme reçue', section: 'Actions', run: function(){ toast('PO-4460 marquée comme reçue', 'success'); } }
  ];

  function fuzzyMatch(query, text){
    query = query.toLowerCase();
    text = text.toLowerCase();
    var qi = 0;
    for (var ti = 0; ti < text.length && qi < query.length; ti++){
      if (text[ti] === query[qi]) qi++;
    }
    return qi === query.length;
  }

  function renderList(){
    var query = input.value.trim();
    var filtered = commands.filter(function(c){
      return query === '' || fuzzyMatch(query, c.label + ' ' + c.section);
    });

    if (filtered.length === 0){
      list.innerHTML = '<li class="command-empty">Aucun résultat pour « ' + query + ' »</li>';
      return;
    }

    list.innerHTML = filtered.map(function(c, i){
      return '<li class="command-item' + (i === activeIndex ? ' active' : '') + '" data-index="' + i + '">' +
        '<span>' + c.label + '</span><span class="command-item-section">' + c.section + '</span></li>';
    }).join('');

    list.__filtered = filtered;

    Array.prototype.forEach.call(list.querySelectorAll('.command-item'), function(item){
      item.addEventListener('mouseenter', function(){
        activeIndex = parseInt(item.getAttribute('data-index'), 10);
        renderList();
      });
      item.addEventListener('click', function(){
        runActive();
      });
    });
  }

  function runActive(){
    var filtered = list.__filtered || [];
    var cmd = filtered[activeIndex];
    if (cmd){ cmd.run(); }
    closePalette();
  }

  function openPalette(){
    lastFocused = document.activeElement;
    activeIndex = 0;
    input.value = '';
    overlay.classList.add('open');
    renderList();
    setTimeout(function(){ input.focus(); }, 50);
  }

  function closePalette(){
    overlay.classList.remove('open');
    if (lastFocused) lastFocused.focus();
  }

  searchTrigger.addEventListener('click', openPalette);

  overlay.addEventListener('mousedown', function(e){
    if (e.target === overlay) closePalette();
  });

  input.addEventListener('input', function(){
    activeIndex = 0;
    renderList();
  });

  document.addEventListener('keydown', function(e){
    var isOpen = overlay.classList.contains('open');
    if ((e.metaKey || e.ctrlKey) && e.key.toLowerCase() === 'k'){
      e.preventDefault();
      isOpen ? closePalette() : openPalette();
      return;
    }
    if (!isOpen) return;

    if (e.key === 'Escape'){ e.preventDefault(); closePalette(); }
    else if (e.key === 'ArrowDown'){
      e.preventDefault();
      var max = (list.__filtered || []).length - 1;
      activeIndex = Math.min(activeIndex + 1, max);
      renderList();
      var el = list.querySelector('.command-item.active');
      if (el) el.scrollIntoView({ block: 'nearest' });
    } else if (e.key === 'ArrowUp'){
      e.preventDefault();
      activeIndex = Math.max(activeIndex - 1, 0);
      renderList();
      var el2 = list.querySelector('.command-item.active');
      if (el2) el2.scrollIntoView({ block: 'nearest' });
    } else if (e.key === 'Enter'){
      e.preventDefault();
      runActive();
    }
  });

})();

(function(){
  "use strict";

  /* ---------- Nav scroll shadow ---------- */
  var nav = document.getElementById('siteNav');
  window.addEventListener('scroll', function(){
    nav.classList.toggle('scrolled', window.scrollY > 10);
  }, { passive: true });

  /* ---------- Nav scroll-spy underline ---------- */
  var navLinks = Array.prototype.slice.call(document.querySelectorAll('.nav-link'));
  var underline = document.getElementById('navUnderline');
  var sections = navLinks.map(function(link){
    return document.getElementById(link.getAttribute('data-target'));
  });

  function setActiveLink(link){
    navLinks.forEach(function(l){ l.classList.toggle('active', l === link); });
    underline.style.left = (link.offsetLeft) + 'px';
    underline.style.width = link.offsetWidth + 'px';
    underline.classList.add('ready');
  }

  var spyObserver = new IntersectionObserver(function(entries){
    entries.forEach(function(entry){
      if (entry.isIntersecting){
        var idx = sections.indexOf(entry.target);
        if (idx !== -1) setActiveLink(navLinks[idx]);
      }
    });
  }, { rootMargin: '-40% 0px -50% 0px', threshold: 0 });

  sections.forEach(function(s){ if (s) spyObserver.observe(s); });

  navLinks.forEach(function(link){
    link.addEventListener('click', function(e){
      e.preventDefault();
      var target = document.getElementById(link.getAttribute('data-target'));
      if (target) target.scrollIntoView({ behavior: 'smooth', block: 'start' });
    });
  });

  /* ---------- Generic scroll reveal ---------- */
  var revealEls = document.querySelectorAll('[data-reveal]');
  var revealObserver = new IntersectionObserver(function(entries){
    entries.forEach(function(entry, i){
      if (entry.isIntersecting){
        entry.target.classList.add('in-view');
        revealObserver.unobserve(entry.target);
      }
    });
  }, { threshold: 0.15 });
  revealEls.forEach(function(el, i){
    el.style.transitionDelay = (i % 4) * 60 + 'ms';
    revealObserver.observe(el);
  });

  /* ---------- Hero mockup parallax tilt ---------- */
  var heroVisual = document.getElementById('heroVisual');
  var mockupCard = document.getElementById('mockupCard');
  heroVisual.addEventListener('mousemove', function(e){
    var rect = heroVisual.getBoundingClientRect();
    var relX = (e.clientX - rect.left) / rect.width - 0.5;
    var relY = (e.clientY - rect.top) / rect.height - 0.5;
    mockupCard.style.transform = 'rotateY(' + (relX * 8) + 'deg) rotateX(' + (relY * -8) + 'deg)';
  });
  heroVisual.addEventListener('mouseleave', function(){
    mockupCard.style.transform = 'rotateY(0deg) rotateX(0deg)';
  });

  /* ---------- Magnetic CTA ---------- */
  var magneticBtn = document.getElementById('magneticBtn');
  magneticBtn.style.transition = 'transform 180ms ' + getComputedStyle(document.documentElement).getPropertyValue('--ease');
  magneticBtn.addEventListener('mousemove', function(e){
    var rect = magneticBtn.getBoundingClientRect();
    var relX = e.clientX - rect.left - rect.width / 2;
    var relY = e.clientY - rect.top - rect.height / 2;
    magneticBtn.style.transform = 'translate(' + (relX * 0.22) + 'px,' + (relY * 0.35) + 'px)';
  });
  magneticBtn.addEventListener('mouseleave', function(){
    magneticBtn.style.transform = 'translate(0,0)';
  });

  /* ---------- Count-up stats ---------- */
  function easeOutCubic(t){ return 1 - Math.pow(1 - t, 3); }

  function animateValue(el){
    var target = parseFloat(el.getAttribute('data-target'));
    var suffix = el.getAttribute('data-suffix') || '';
    var decimals = parseInt(el.getAttribute('data-decimals') || '0', 10);
    var duration = 1200;
    var start = null;

    function frame(ts){
      if (start === null) start = ts;
      var progress = Math.min((ts - start) / duration, 1);
      var current = target * easeOutCubic(progress);
      var display = decimals > 0
        ? (current / Math.pow(10, decimals)).toFixed(decimals)
        : Math.round(current).toLocaleString('fr-FR');
      el.textContent = display + suffix;
      if (progress < 1) requestAnimationFrame(frame);
      else{
        var finalVal = decimals > 0 ? (target / Math.pow(10, decimals)).toFixed(decimals) : target.toLocaleString('fr-FR');
        el.textContent = finalVal + suffix;
      }
    }
    requestAnimationFrame(frame);
  }

  var statEls = document.querySelectorAll('.stat-value[data-target]');
  var statObserver = new IntersectionObserver(function(entries){
    entries.forEach(function(entry){
      if (entry.isIntersecting){
        animateValue(entry.target);
        statObserver.unobserve(entry.target);
      }
    });
  }, { threshold: 0.5 });
  statEls.forEach(function(el){ statObserver.observe(el); });

  /* ---------- Agents IA: start the relay once the section is visible ---------- */
  var agentsSection = document.getElementById('agents');
  if (agentsSection){
    var agentsObserver = new IntersectionObserver(function(entries){
      entries.forEach(function(entry){
        if (entry.isIntersecting){
          agentsSection.classList.add('in-view');
          agentsObserver.unobserve(agentsSection);
        }
      });
    }, { threshold: 0.25 });
    agentsObserver.observe(agentsSection);
  }

  /* ---------- Sticky scroll showcase ---------- */
  var showcaseSteps = document.querySelectorAll('.showcase-step');
  var showcaseStates = document.querySelectorAll('.showcase-state');

  function setActiveStep(stepNum){
    showcaseSteps.forEach(function(step){
      step.classList.toggle('active', step.getAttribute('data-step') === stepNum);
    });
    showcaseStates.forEach(function(state){
      state.classList.toggle('active', state.getAttribute('data-state') === stepNum);
    });
  }

  var showcaseObserver = new IntersectionObserver(function(entries){
    entries.forEach(function(entry){
      if (entry.isIntersecting){
        setActiveStep(entry.target.getAttribute('data-step'));
      }
    });
  }, { rootMargin: '-45% 0px -45% 0px', threshold: 0 });
  showcaseSteps.forEach(function(step){ showcaseObserver.observe(step); });

  /* ---------- Pricing billing toggle ---------- */
  var billingSwitch = document.getElementById('billingSwitch');
  var labelMonthly = document.getElementById('labelMonthly');
  var labelAnnual = document.getElementById('labelAnnual');
  var saveBadge = document.getElementById('saveBadge');
  var priceNums = document.querySelectorAll('.price-num[data-monthly]');
  var isAnnual = false;

  function applyBilling(){
    billingSwitch.classList.toggle('on', isAnnual);
    billingSwitch.setAttribute('aria-checked', String(isAnnual));
    labelMonthly.classList.toggle('active', !isAnnual);
    labelAnnual.classList.toggle('active', isAnnual);
    saveBadge.classList.toggle('show', isAnnual);
    priceNums.forEach(function(el){
      el.style.opacity = '0';
      setTimeout(function(){
        el.textContent = isAnnual ? el.getAttribute('data-annual') : el.getAttribute('data-monthly');
        el.style.opacity = '1';
      }, 140);
    });
  }

  function toggleBilling(){ isAnnual = !isAnnual; applyBilling(); }

  billingSwitch.addEventListener('click', toggleBilling);
  billingSwitch.addEventListener('keydown', function(e){
    if (e.key === 'Enter' || e.key === ' '){ e.preventDefault(); toggleBilling(); }
  });

  /* ---------- FAQ accordion ---------- */
  var faqItems = document.querySelectorAll('.faq-item');
  faqItems.forEach(function(item){
    var question = item.querySelector('.faq-question');
    var answer = item.querySelector('.faq-answer');
    question.addEventListener('click', function(){
      var isOpen = item.classList.contains('open');
      faqItems.forEach(function(other){
        if (other !== item && other.classList.contains('open')){
          other.classList.remove('open');
          other.querySelector('.faq-answer').style.maxHeight = '0px';
        }
      });
      if (isOpen){
        item.classList.remove('open');
        answer.style.maxHeight = '0px';
      } else {
        item.classList.add('open');
        answer.style.maxHeight = answer.scrollHeight + 'px';
      }
    });
  });

})();
